# 从接手到可交付：完整施工流程

## 先确定产品是什么

先写一段能检验的目标：角色是谁、桌面构图是什么、哪只手负责键盘、鼠标如何移动、有哪些表情、在哪个操作系统运行。把美术辨识度、动作反馈、原生能力、设置和发布依次排列。

用户要求桌宠时，优先完成陪伴本身。番茄钟、待办、计时器、联网聊天、复杂游戏系统都会增加状态与界面负担；没有明确需求就不加入。不要为了功能数量牺牲动作质量。

## 阶段 0：接手盘点

读 AGENTS、Git diff、最近提交和进度文件，定位当前生效的模型入口。先运行能跑的现有工程，再读相关模块。只把真正缺失的东西放进待办。

记下 Node、Rust、Python、WebView/浏览器、Cubism Editor、SDK/Core 和模型版本。确认 CLI 与工具实际存在，不把“安装过”当作“当前能用”。磁盘紧张时查依赖、构建缓存和历史素材大小；先保护交付包与可编辑模型。

输出一张工作表：需求、对应模块、当前状态、证据、下一步。它只服务施工，不能把“代码里有选项”当作“功能完成”。

## 阶段 1：先跑通垂直切片

最小切片应包含真实模型加载、呼吸/眨眼、一次键盘反馈、一次鼠标反馈、设置打开和原生窗口启动。这样可以尽早发现 SDK、WebGL、资源路径、原生事件或打包问题。

缺少精细图层时，可以先用明确标注的占位模型验证程序结构，但必须保留接入正式模型的边界。截图贴图轻轻晃动不等于正式 Cubism 绑定，SVG 动效也不等于 Live2D。

## 阶段 2：原画分层与遮挡补全

按参考图建立层级和遮挡关系表。先补全鼠标、脸、身体、键盘、发束与凤凰被遮住的区域，再拆出可动手、袖口、前后发和饰品。把层与功能一一对应，避免没有动作用途却大量细拆。

用原图对齐检查头发数量、脸轮廓、眼距、饰品位置和衣服结构。每轮只改变一个主要问题，保存候选图与对照证据；不要一轮同时大改脸、眼、发色和头部比例。

实际源稿需有可编辑层。生成图像可以提供候选补画，但不能自动证明它可用于 Cubism 变形。正式图层要在运动极值下没有缺口、残边或明显补丁。

## 阶段 3：Cubism 绑定与导出

在编辑器中建 ArtMesh、变形器、关键形、参数与物理。优先头角度、眼睛开合/视线、嘴、呼吸、双手按压和二维伸手；再做发束、饰品、凤凰等次级动作。

保存 `.cmo3`，导出 moc3/model3/贴图/physics/motion/expression，运行依赖检查。保留导出时使用的源文件、参数清单和纹理版本。不要把临时运行时补丁倒称为“已在编辑器完成”。

导出后先在实际运行时加载，再检查组合参数极值。编辑器内正确的图层在自定义渲染器里仍可能因为混合、遮罩或排序而出错。

## 阶段 4：把动作做成反馈系统

输入是触发，动作是连续状态。语义输入先经过动作机，再生成渲染快照，最后驱动模型。不要让每个按钮各自写一套互相抢参数的动画。

键盘按压、伸手位置、鼠标位移、头部弹性和表情分别保留状态，再按优先级组合。按键松开时释放按压，位置可以稍后自然回到中间。重复按同区仍需新的动作起点。

先做正确映射，再调幅度。手按错区时不能用更大弹性掩盖。鼠标与手不同步时不能只增大手的平移量。

## 阶段 5：原生桌面体验

全局输入和空闲动作在启动后直接运行。设置是交互窗口，桌宠是陪伴窗口，二者的激活/置顶策略需要不同。右键菜单应尽量在主体旁边弹出，并能稳定拖动。

拖拽、磁吸、缩放、全屏避让和多屏定位统一坐标体系。优先检查当前用户遇到的底边或焦点问题，再扩展到其他显示器。不要用整块透明窗口的矩形代替可见角色的边界。

## 阶段 6：界面与设置

连续缩放、动作强度、按键显示、气泡、窗口置顶/穿透等放进清晰分类。相似控件保持同一尺寸、间距和状态风格。开关文案表达结果而非技术实现。

设置保存需要失败反馈；不要把滑条拖动几十次变成几十个未完成的文件写入。预览、合并更新、最终提交和失败回滚应能解释清楚。

## 阶段 7：针对性验收与发布

模型改动做视觉极值检查；动作改动做相关输入切换；Rust/窗口改动启动实际打包程序验证；文档整理检查引用。已有检查通过后不要无原因循环重测。

只给当前目标平台的程序做相应声明。Windows 主机不能独立证明 macOS app 可启动；用户提供 MacBook 实测时标注“用户实测”。

按版本保存 EXE/安装包、模型、可编辑源、许可证、校验和、源码提交和剩余问题。交付时列出已实现、已验证、未完成，不把“能打包”写成“全部完成”。

## 高效推进的规则

- 先用源码、模型清单、CLI 和直接 API 定位问题；需要看实际图像或编辑器状态时再用界面操作。
- 独立读取可以并行；依赖操作、修改、发布和审批按顺序做。
- 同一报错重复两次时改变诊断方法，先确认权限、路径、进程和输入假设，不盲点第三遍。
- 修复前保存可复现的坏状态；修复后检查同一个状态。不要不断发明新测试，把本来的问题晾在一边。
- 一轮解决一个可见问题，保存，再进入下一个。大改之前留回退点；长构建之前先写进度。
- 用检查结果回答具体问题：例如“脸部补片跟随头转是否连续”，而不是笼统“做了几十个测试”。
